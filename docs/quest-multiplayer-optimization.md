# v3.3.8 任务系统多人性能优化与服主验证

本次针对多人收集物品、背包变动带来的重复计算和集中处理，未修改 Chest UI、任务定义或奖励规则。沿用 MCBE 1.26.52 构建基线。

## 已实施

- 玩家任务缓存命中时直接复用聚合数据；首次读取、新名字迁移、损坏检测与恢复继续走原流程。
- 无关事件在读取任务存档前退出；事件类型判断改为 Set 查询。
- 只在事实、历史完成状态或本次任务完成后，执行额外的自动接取扫描。已有当前任务先跳过，不再反复做可用性检查。
- 每轮检查复用规则上下文；完成状态变化后立即使该上下文失效，后续任务使用最新状态。
- 静态可用性元数据缓存随目录重建或预设开关改变失效，保留任务包开关、定义编辑、能力判断和奖励覆盖。
- 任务处理使用已建立的事件索引定义；历史 Boss 回填只检查匹配的目标；快照只检查关联 provider 的目标。
- 背包/装备快照仅在进度值、类型或 provider 版本变化时触发保存。刷新时间保留在内存，随实际进度变化保存，不再单独触发完整保存。
- 物品增量按玩家轮转处理，保留每种物品的数量和每位玩家的排队顺序。物品队列和快照消费者共享每 tick 4 ms / 64 项的协作预算；快照同时保留每批最多 8 人的限制。
- 预算到达后把剩余工作留到后续 tick，不通过减少进度来降低开销。时间预算检查发生在工作开始前，无法中断正在执行的单项工作，单项重保存仍可能超过 4 ms。
- 使用物品只刷新背包、装备和效果，避免每次额外遍历领地/坐标。首次进服、接取任务仍刷新完整状态；相关业务成功事件仍刷新领地/坐标/公会证据。
- 关闭任务系统时清理延期物品与快照任务；快照处理后释放玩家句柄引用。

本次保留进度真实变化时的即时保存，以及奖励领取的幂等、双代存储和恢复机制。没有修改所有周期采样或引入异步奖励保存。

## 本地验证

已通过 `npm run check`（lint、类型检查、480 个测试）。新增验证涵盖：

- 50 人无变化快照和无变化物品事件：缓存不深复制，不写存档。
- 100 人同时获得两类物品：200 条事件、600 件数量全部保留，逐 tick 分批，按玩家轮转。
- 100 人快照队列：与其他延期工作共享时间预算，重复标记合并，最终全部消费。
- 新别名迁移一次、任务定义和预设开关改变后缓存失效。
- 事实解锁、完成后接取后续任务、解锁事件排除策略、精确累计数量、完成快照。
- 关闭功能后不会重放旧的排队工作。

同一份审计脚本对优化前后真实任务代码的 Node 模拟结果（已预热，无额外历史实例）：

| 工作量 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 8 人无变化背包快照消费者 | 31.23 ms | 0.25 ms |
| 50 人无变化背包消费者总成本 | 192.21 ms | 1.29 ms |
| 50 人各一次无进度变化物品事件 | 371.89 ms | 1.03 ms |
| 50 人背包快照的动态属性写/删除调用 | 150 | 0 |
| 50 人无变化物品事件的 JSON 序列化 | 48550 | 0 |

这是当前机器上的脚本比较，不是服务器 TPS 提升承诺。Minecraft 引擎、HUD、原生背包组件与真实动态属性成本由模拟边界替代；毫秒还受 JIT、GC 和机器负载影响。快照的 50 人总成本在生产队列中分多批执行。200 个历史实例场景为人为压力数据，不代表默认玩家都拥有该数量。

仓库中可重复执行：

```powershell
node tools/benchmark-quest-performance.cjs
node --test tests/quest-performance.test.cjs tests/quest-snapshot-budget.test.cjs tests/quest-event-adapters.test.cjs
```

基准包含 20/50/100 名模拟玩家，无变化背包、无关物品、获得铁锭触发实际事实保存三种工作量，以及 0/200 条额外历史实例。它输出串行总成本与属性调用次数，不测引擎 TPS 或生产队列延迟。

## 发给服主的安装与验证步骤

1. 停服后备份世界及当前模组包；安装与原来相同变体的 v3.3.8 行为包和资源包，更新世界中相应包版本。原来用普通兼容版继续用普通兼容版；原来用 BDS 增强版继续用增强版。不要同时启用两份苦力怕菜单。保留原世界和任务数据，启动后确认包显示 3.3.8。
2. 在任务系统开启、任务配置不变的条件下，尽量用相近在线人数比较旧版与新版，每轮持续约 10 分钟。记录在线人数、服务器已有 TPS/耗时统计以及方块破坏、打开容器的实际延迟。客户端 FPS 不能替代服务器 TPS。
3. 让多名玩家同时正常挖矿、捡掉落物、从箱子取不同物品、整理背包、连续放置方块和使用物品。重点观察原来“有人操作就卡”的情况是否减轻；没有增加任务相关物品时，整理背包也应能流畅进行。
4. 选择现有获得类和背包持有类任务核对进度。连续分批获得所需物品后，进度应完整累计；移动同一批物品不应使持有数量翻倍。完成前置任务后，后续任务应正常接取。大量同时拾取时允许任务提示等待若干 tick，待队列处理完后再核对最终进度。
5. 完成一项任务并领取一次奖励，确认没有重复发放；重进服务器并正常停服重启，检查任务进度和已领取状态。创建或使用现有相关业务功能，确认领地、坐标、公会等任务仍能正常推进。

反馈建议附：变体、实际游戏/BDS 版本、在线人数、发生卡顿的具体行为、任务包/自定义任务数量、同场景前后的 TPS/延迟，以及内容日志中 Quest 相关异常。剩余问题应根据这些实际场景继续定位，不能仅按模拟数字判断已完全解决。
